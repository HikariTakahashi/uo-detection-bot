# Pi上の未知変換審査と本番カウント

Macは開発・初回配置にだけ使う。稼働中はPiのGo BotがDiscordとカウントを管理し、loopbackの復元サービス、既存Laya、systemd timerが処理を進める。

## 状態と返信

`adaptive.json` の `enabled: true` で有効。未設定なら既存処理を維持する。対象チャンネル・対象語・Bot/Webhook/DM除外は既存検知設定を継承する。完全一致・既存の連続語は従来処理、それ以外は永続審査キューが排他的に担当する。

固定変換と承認済み復元器は共通の探索で使用する。元本文の完全一致・既存の繰り返し一致は従来どおり、それ以外は永続キューが担当する。各段で固定変換とselectorが合う承認済み復元器の候補を集め、同じ本文への経路はまとめる。明示的な形式接頭辞は対応復元器が担当する。最大8段・32本文・探索60秒で、循環、候補競合、未対応の残り、実行失敗は加算しない。既存固定変換に加え、UTF-8の16進や外側のpercent・Unicode escape・Ascii85等を、登録語がまだ見えない中間層にも適用する。候補が増えた結果、一部の数値列は従来より保守的に保留になる。

復元探索が一意に完了した本文は、具体的な形式候補が残る場合だけ未知変換として審査する。AIの符号化疑い・入力制限だけでは審査通知を出さず、通常の対象語判定へ進める。対象語のない本文や引用・説明は対象外、対象語のある発言は従来の冷笑判定を行う。形式接頭辞・符号列形状・未対応の内層、復元の競合や失敗による保留は維持する。判定方針の版が変わるため、既存の誤保留投稿も通常の再判定で対象外として完了する。

一意に復元した本文全体の完全一致・繰り返し一致は、既存Goルールの件数を使用する。対象語・既存の連続語の末尾に `? ! ？ ！` だけが付く場合も同じ件数を使用し、Layaを呼ばず確定する。空白・引用・周辺の文章は除去しない。`うおw` 等は復元後の本文をLayaへ渡す。初回に冷笑と確定した投稿には通常の「冷笑を検知しました！」（複数件なら既存の件数文面）と加算後累計を1件返信する。審査中・保留を経た投稿だけに「再判定完了」を付ける。初回保留も通知・保存し、次のリリースで再判定する。過去の審査返信の文面と待機状態から履歴を識別するため、今回の変更による台帳スキーマ追加はない。

固定変換の二重実装を避けるため、runtimeは同じ配布パッケージの `discord-bot-linux-arm64 -restore-view` を各本文に対して呼び出す。このモードはstdin/stdoutだけを使い、Discord・カウント・設定・資格情報を開かない。生成されたPythonは引き続きDockerだけで実行する。helperは配布manifestの検証対象で、バイナリハッシュも判定方針の版に含める。別版や欠損したhelperのまま本番へ反映しない。

未知変換は元投稿に1件だけ返信し、加算しない。審査記録には投稿/チャンネル/サーバー/投稿者ID、本文、編集時刻、版ハッシュ、最新の返信ID・過去の返信ID一覧、復元機能の版と状態を保存する。既定では原文を外部生成サービスへ送信しない。未知方式の推定に限り、後述の明示的なチャンネル・入力範囲の設定で例外を許可できる。審査用ディレクトリは0700、記録は0600。待機上限1000件。上限では受付失敗をログに記録し加算しない。

新しい承認済み復元リリースまたは判定方針の版を検知すると待機投稿を再取得して判定する。現在はすべての保留投稿を候補に再確認するため、無関係な復元器追加でも再確認される場合がある。復元の適用はselectorで限定する。対応しない投稿は加算せず次版を待つ。既知復元器が拒否した入力でも、新しい独立検証契約で候補を特定できる場合は準備を更新する。ERROR/TIMEOUTの生成依頼を自動再送することはない。

返信文面は次のとおり。

```
冷笑の疑いがあるメッセージを検知しました！
<@{userId}>さんのメッセージは現在審査中です！
```

```
**再判定完了**
冷笑を検知しました！
<@{userId}>さんの{回数}回目の冷笑です！
```

```
**再判定完了**
冷笑ではありませんでした。
```

```
**審査継続**
判定が保留されました！
<@845282954636951583>、なんとかしろ！
```

再判定の結果（加算あり・対象外・保留）は、元投稿への新しい返信として各判定につき1件送る。最初の審査中の返信と過去の結果は編集せず残す。同じ本文版・同じ復元機能版の再試行では追加送信しない。保留は次のリリースで再判定したときに新しい結果を返信する。既存の完了済み審査は移行だけでは再送しない。メンション許可は指定ユーザーだけ。返信送信前にsendingを永続保存する。送信の応答が失われた場合、Bot自身の元投稿への返信のうち、前回の返信より新しく今回の文面と一致するものを履歴から照合し、別のPOSTを自動発行しない。履歴で照合できない場合は `review reply delivery unresolved` として運用者の確認を待つ。この場合まで「必ず自動で1返信」を保証する設計ではない。手動削除されたBot返信も再作成しない。

新形式の審査記録には `notice_version` と `reply_history` を保存する。旧版からの移行では未完了の返信編集だけを新規返信へ切り替える。旧バイナリは追加フィールドを読めないため、移行後のロールバックにはこの形式を扱える修正版を使い、審査台帳やカウントを過去のバックアップで上書きしない。

冷笑ワード件数を累計へ反映する。投稿全体に1つのラベルを付けて全語を加算せず、対象語のある文を判定する。どの文か不確かな場合は投稿を保留する。1投稿に複数語がある場合は複数回になる。通知の `{回数}` は加算確定時点の累計。

`counts.json` はreview_receiptsを含むversion 2に移行する。累計と投稿ごとの加算結果は同じファイルへ原子的に保存する。結果の返信送信を再試行しても再加算しない。審査ファイル更新直前のクラッシュでも、receiptから確定済みの累計を復元する。編集された投稿は最新版を取得し、以前の審査による寄与だけを取り下げて判定し直す。削除された未完了審査は取り消し、保存している審査中・結果のBot返信も削除する。完了済みの履歴を削除しても確定カウントを遡って取り消す運用ではない。

## Piの各サービス

- `discord-bot.service`: Gateway、審査台帳、返信、カウント。既存Bot資格情報を保持。
- 既存user unit `laya-shadow.service`: `/adaptive/detect` と `/adaptive/judge` を追加。固定済みのオフラインモデルを使用。
- `laya-decoder.service`: 127.0.0.1:8767。生成コードはネットワークなし・読み取り専用・非rootのDockerのみで実行。Python runner内部にもメモリ/CPU上限を設定し、Piのmemory cgroup無効時を補完。
- `laya-decoder-update.timer`: 2分ごとに `/etc/laya-decoder/approved-release.json` の固定commit/indexを確認。検証成功後だけsnapshotへのsymlinkを原子的に切り替える。
- `laya-decoder-generate.timer`: 1分ごとに承認済み合成テンプレートの依頼を進める。従来モードは1状態ディレクトリにつき新規依頼3件まで、自動モードはUTC日ごとに3件まで。POST直前にIDを保存し、応答不明時は同一IDのGETだけ。ERROR/TIMEOUTは自動再送しない。

デコーダーのtrusted controllerはdockerグループを使用するため、そのcontrollerとインストール済みソースはroot所有にする。生成コードにDocker socketや資格情報をマウントしない。Botのユーザーはdockerグループに加えない。

## 合成例・生成・公開・本番採用

未知検知後、Piはroot所有の `/etc/laya-decoder/automatic.json` で許可された公開仕様から、共有用サンプル3件と独立した正常・不正入力の検証契約を自動生成する。この既存の合成復元器生成経路では、実投稿本文・ID・その可逆符号列をLunaへ送らない。未知方式推定の外部送信は別設定で、既定では無効。生成器に渡す仕様と合成例、非共有の検証例は、Lunaの回答より前に固定する。生成コード自身から正解を作らない。

自動許可はroot方針のレシピ一覧に限定する。`x9:` はUTF-8各バイトを `(73*b+41)%256` に置換して大文字hexにする公開仕様。接頭辞なしの16進入力は通常hexとこの逆変換の競合候補として扱い、可読な復元結果が一意の場合だけ進める。これは「仕様も鍵も未知の方式を新たに解読した成功」ではない。方式が特定できないselectorは `needs_format_spec`、競合が残る場合は保留を維持する。

1. 外層・内層を問わず候補方式を最大8段探索し、未導入の復元器を形式ごとに準備する。`x9:` は専用prefix selectorを登録する。明示的なprefix復元器は広いshape復元器より優先する。
2. `laya-decoder-generate.timer` が合成準備、Luna依頼、本人性確認、隔離Dockerでの独立検証を進める。自動モードはUTC日ごとに新規3件まで。上限に達した未送信依頼は翌日へ持ち越す。送信前にIDを保存し、応答不明後はGETのみ。失敗/期限切れ/検証不一致は勝手に再送しない。
3. この合成復元器生成経路では公開可能な仕様・合成例だけをLunaへ送る。正解付き検証例は送らない。候補が全検証を通るまで本番は変更しない。
4. 自動公開方針を別途明示承認して `publish_validated=true` にした場合、`laya-decoder-publication.timer` が専用repoの更新案を作り、独立検証を再実行し、index・当該contract・bundleの最大5ファイルだけをCommit/Pushする。Pi専用トークンに対象repoのContents read/write、Actions readが必要。自動公開を許可していない場合は従来の具体的Commit承認で止まる。
5. 公開前にbase・title・全差分ハッシュを永続化。Commit後/Push応答不明でも同一Commitを再利用し、force pushはしない。差分ドリフト・遠隔競合は停止して既存結果を保持する。未決の本番採用DMがある間は次候補で置き換えない。
6. CI/Release成功と受取側の検証後、指定ユーザーへ本番採用DMを1件送る。DMで承認されてからPiが反映し、既存の待機投稿を最新版で再判定する。対象外・保留は非加算、確定分は台帳で二重加算を防ぐ。

`automatic` 導入モードは、具体的にレビューした自動公開範囲への承認後のみ実行する。BotやMacの資格情報は転用しない。従来のroot所有手動テンプレートは引き続き使用でき、その提案は自動公開の対象外。

## 導入

管理者がレビュー済み `scripts/install-adaptive.sh` をPiで実行する。

1. `prepare`: docker.io/gh/git、専用ユーザー、固定ARM64イメージを準備。本番Botを変更しない。
2. `credentials`: Pi専用GitHub tokenとLuna keyを非表示入力でroot専用ファイルへ保存。systemd LoadCredentialで各サービスに渡す。
3. CIの `decoder-production.tar.gz` と `ADAPTIVE-SHA256SUMS` を固定commitから取得し検証・展開。
4. `install`: runtime/service配置、Layaアダプターのバックアップ・更新、既存11復元器の固定Release再検証。本番カウントはまだ有効化しない。
5. 合成データで復元・再判定・health・権限・復旧を確認。
6. `enable`: 既存累計をバックアップし、新Botとadaptive設定を有効化する。既存チャンネル設定・Botトークンは書き換えない。

初期復元器の固定Releaseは `38a4bbc7bc6686b71745912aee845e8e89fa2520`。復元器11件は評価済みの成果物を明示的な本番承認記録とともに利用する。評価用manifestのscopeを書き換えたり、既存Releaseを上書きしたりしない。

`enable` は更新タイマーを一時停止する。新コードのGitHub main/Releaseと導入済みcommitが一致し、起動とhealthを確認してからBot更新timerを再開する。旧版への自動更新でv2状態を読めなくなることを避ける。

停止は `disable`。adaptiveの新規受付・加算を止め、累計とreceiptを維持する。停止後も動かす旧来の検知ルートとの重複を避けるため、既存レビューreceiptを持つ投稿は従来ルートから加算しない。旧バイナリへ戻すときはv2互換性を確認し、バックアップを現在の累計にそのまま上書きしない。

## Discord DMでの本番採用承認

`install-adaptive.sh approvals` で有効化する。既存の本番版と累計を引き継ぎ、従来の固定版更新timerを停止して `laya-decoder-approval.timer` に切り替える。Botの新しいバイナリと配布ソースを先に配置する必要がある。GitHub資格情報には専用評価リポジトリの Contents read に加えて **Actions read** が必要。

Piの `publication-pushed.json` に記録されたCommit/indexだけを候補にする。専用評価workflowの最新push実行が成功し、Releaseのハッシュ・全復元器の独立検証が通った後、ユーザー `845282954636951583` のDMに「本番採用を許可／却下」のボタンを1件送る。実投稿本文は送らない。合成準備・限定したGitHub自動公開への事前承認を代替しない。自動方針の範囲外は個別承認が必要。

回答期限は依頼作成から7日。催促は送らない。本人・DMチャンネル・Bot返信ID・依頼のハッシュを一致確認する。承認は候補Commit/indexと依頼時の本番版に固定され、候補や本番版の変更、期限切れ、却下では使えない。回答を永続化後、PiはCIと配布物を再検証し、同じ配備ロックの中で基準版の一致を確認して切り替える。成功後は既存の保留再判定を使う。DMは同じメッセージを編集し、反映完了・失敗・却下・失効を表示する。

現在版が承認済みの対象と一致し、記録が反映中なら、切り替え直後のクラッシュとして完了記録を復旧する。旧初期承認ファイルは定期処理で再適用しない。取得などの一時失敗は同じ承認だけで再試行し、検証不一致では旧版を保持して停止する。

承認連携は `/var/lib/laya-approvals` 配下だけを専用グループで共有する。requests/resultsはlaya-decoderのみ書き込み、decisionsはdiscord-botのみ書き込む。BotのDM送信記録は `/var/lib/discord-bot/release-approvals` に0700/0600で保存する。BotにsudoやDocker権限を追加しない。

DM拒否時はblocked記録を保持し、公開チャンネルへ転送しない。POST応答不明はBot自身のDM履歴を照合し、見つからなければ再POSTせず運用者確認を待つ。手動で消されたDMも自動再作成しない。却下・失効済みの同じ候補は再通知しない。再依頼が必要な場合は、通常のapprovalサービスと同じユーザー・資格情報・環境で `approval.py` に `--retry-request <終了済み依頼ID>` を指定する。再検証後に新しい依頼ID・期限で作成する。

Piで確認した配備条件として、3つのdecoderサービスのTMPDIRは書き込み可能な専用StateDirectoryを使う。runtime制御プロセスの仮想アドレス上限はDocker CLIが起動できる2GiB、生成コード内部のアドレス上限は128MiBを維持する。Lunaリレーへの通信はアプリ名のUser-Agent `uo-decoder-pi/1.0` を明示する。

## 接頭辞なし・多重変換の候補準備

`automatic` の許可範囲は x9、接頭辞なし16進候補群（通常のUTF-8とx9逆変換）、Base64、Base32、percent、Unicode escape。形式の見た目だけで鍵や本文を決めず、ローカルの厳密な逆変換・UTF検証と独立した前向きエンコーダーを根拠に候補を絞る。16進候補が複数の異なる可読本文を返す場合は保留し、対象ワードに近い候補を優先しない。通常の16進復元器を承認済みでも、新しい競合候補契約の承認を代用できない。

候補推定は最大8段。実投稿や中間の復元本文はPi外へ送らず、発見記録には形式・候補方式・深さだけ保存する。候補による復元は合成データ準備のためだけに使い、本番の判定・加算には使わない。追加復元器として実行されるのはLunaが生成し、固定した独立契約、GitHub CI、Piの受取側検証、本番採用DM承認を通った復元器のみ。途中の未対応形式も準備し、複数の復元器が必要なら各リリースの承認後に次の候補を公開する。1日3依頼、各公開は復元器・契約・indexの最大5ファイル、force push禁止を維持する。

本番稼働中はPiで完結する。仕様自体が未知で独立した正解を作れない形式、候補競合、探索上限、生成失敗は自動採用しない。この変更で任意の暗号方式・未知鍵を復元できるようになるわけではない。

## 共通検知フローの更新手順（承認後）

1. 差分・テスト結果を提示し、具体的Commit案の承認を受けてからCommit/Pushする。mainのCI成功後は既存Bot更新timerが自動配布するため、統合更新時は先にtimerと進行中の更新を停止して版の混在を避ける。
2. 成功した固定commitのBotとdecoder-productionアーカイブを取得し、SHA256と内部manifestを検証する。新しいruntimeディレクトリには `services`・`experiments` と**同じ版のhelperバイナリ**を含める。
3. 対象サービスを止めて台帳を保全し、Botとruntimeの両方を同じcommitに切り替える。**既存13復元器・active-production・DM承認・自動公開ポリシーは維持する**。既存環境の更新で、初期復元器導入やcredentials/automatic/approvalsの再設定はしない。
4. カウント資格情報のない独立コピーで合成受け入れテストを実行し、loopback health、helper、サービス起動を確認する。本番に合成投稿を送らない。確認後、通常処理と更新timerを再開する。既存完了投稿を再キューしない。
5. 不具合時はBotとruntimeを同時に直前の互換版へ戻す。現行の台帳・receipt・承認済み復元器は保持し、バックアップで累計を巻き戻さない。

再現用テスト: `go test -race ./...`、`go vet ./...`、`python3 -m unittest discover -s scripts -p 'test_*.py'`、`python3 -m unittest discover -s experiments/laya -p 'test_*.py'`。`scripts/evaluate-unified.py` は承認済みregistryの独立コピーと実Layaで合成11件を検証する。実行結果の `initial-bare.result` をJSONに保存し、`UO_UNIFIED_RESPONSE=<そのJSON> go test ./cmd/discord-bot -run TestUnifiedInitialDetectionAndRestart -v` で通常返信・再起動・応答喪失時の重複防止まで接続検証できる。Discord送信はfake、カウントは一時ファイルだけで行う。

通常日本語の誤審査4件を基に、投稿IDとメンションを合成値に置き換えた公開用回帰例を `scripts/fixtures/readable-japanese.json` に置く。隔離Pi検証に `--readable-regressions scripts/fixtures/readable-japanese.json` を付けると合成11件にこの4件を追加する。結果の4件をfixtureのケースIDから `result` へのJSONオブジェクトとして保存し、`UO_READABLE_RESPONSES=<そのJSON> go test ./cmd/discord-bot -run TestReadableJapaneseNoNoticeAndHeldResolution -v` で、実推論の結果から新規通知なし・既存保留の完了・再起動後の重複防止まで確認できる。実投稿そのものの検証は非公開のローカル入力で行い、その識別子や投稿へのリンクを外部生成・公開用データへ追加しない。

## 未知方式の推定（本番採用とは別のキュー）

未知方式の推定は `services/decoder/estimation.py` が担当する。形式未特定の依頼は `estimate-<64桁ハッシュ>`、Luna通信は別の `luna-<UUID>` を使用する。承認済み復元器のfamily/selectorは登録時に不要で、独立検証後に初めて対応付ける。推定キュー・回答・候補は本番registryへ読み込まない。採用済みregistryだけを使う既存の加算処理を維持する。

自動受付は、隠し区切り文字で分割されたトークン、長く文字種の多い16進列、複数種の記号を使うASCIIトークンなど、入力そのものの具体的な兆候に限る。通常の日本語やAIの符号化疑いだけでは推定キューへ入れない。URL、普通の短いID・単語、通常の絵文字列を根拠にしない。ただし長い数字・16進IDは暗号列と外見が重なるため、誤受付が残る。逆順の短い日本語など、客観的な兆候がないものは明示指定が必要。

指定レビューロールは `/estimate input:<推定対象の文字列だけ>` で明示登録できる。最大400文字。投稿者や返信元を自動で付加しない。`/estimate request_id:<依頼ID>` は現在の状態だけを非公開応答で返す。外部送信許可を代替するコマンドではない。Botの検知対象チャンネル外や指定ロールのない利用者からは受け付けない。

### 外部送信方針の変更点

従来は公開仕様から作った合成例だけをLunaへ送った。新経路では、管理者が許可した場合だけ、方式を推定するために実投稿由来の符号列そのものを送れる。この符号列は内容を復元できる可能性があり、匿名化済み・機密でないとは扱わない。投稿者ID・元投稿ID・チャンネルID・メンション・返信元・周辺文脈は送信プロンプトに付加しない。メンション、メールアドレスなど `@` を含む入力や単独のDiscord IDらしい入力は送信せず、必要なら利用者が範囲を選び直す。自動受付はトークン全体、コマンドは利用者が選んだ文字列だけを対象にする。

`/etc/laya-decoder/estimation.json` はroot所有、group/other書込不可。未設定時と `estimation.config.example.json` は実投稿・合成とも新経路の送信が無効で、ローカル登録だけが可能。既存 `automatic.json` の承認をこの送信許可へ流用しない。

次は**別途レビュー後に実投稿の明示選択部分の送信を許可する設定例**であり、自動適用しない。例のチャンネルIDを実際の許可先へ置き換える。

```json
{
  "schema": 1,
  "external_enabled": true,
  "synthetic_enabled": false,
  "channel_ids": ["123456789012345678"],
  "input_scopes": ["explicit_selection"],
  "max_chars": 200
}
```

`whole_message` を許可しなければ、自動受付した実投稿は未送信のまま待機する。利用者が同じ入力を明示選択すると、未送信依頼の同じIDのまま選択の同意を更新できる。送信後は同意変更や再起動を理由に再POSTしない。`synthetic_enabled` は、操作者が公開可能な合成データとして登録した入力だけの別許可である。

既知の外層を復元した後に未知の符号列が残る場合、その内側の文字列は `restored_payload` という別範囲にする。`whole_message` の許可を復元後本文の送信へ流用しない。復元後は秘匿されていた情報がより直接読める可能性があるため、この範囲も設定例では許可していない。

例えば推定対象を `rr:tac` と明示指定した場合、Lunaへ渡すデータ部分は `観測入力: "rr:tac"` だけとなる。方式や元文を先に正解として渡さず、最大3候補または推定不能を求める。実際の全リクエスト例は `docs/estimation-request.example.json` にあり、投稿者や返信元を含まない。これは合成例で、実際には送信していない。

### 状態、上限、再起動

`/var/lib/laya-decoder/estimation` は0700、依頼・回答・候補は0600で保存する。選択部分だけを保存し、選択外の文脈は保存しない。ローカルのchannel_idは送信許可の照合にだけ使い、Lunaへ渡さない。入力・本文版・判定版・チャンネル・由来で重複を防ぎ、最大1000件。選択を含む同じ入力の未送信依頼は重複作成しない。

| 状態 | 意味 |
|---|---|
| `queued` | 依頼待ち。外部送信無効・許可範囲外・上限到達・接続不可も理由を分けて保存 |
| `awaiting_reply` | POST前に永続化済み。回答待ち。応答不明時も同じIDのGETだけ |
| `unable` | 正しいLuna本人の回答が推定不能だった |
| `validating` | 候補を隔離Dockerで実行中。加算には使わない |
| `unverified` | 候補あり・未検証。実行結果や可読性、往復変換は正しさの証明にならない |
| `awaiting_adoption` | 独立検証済み。公開と本番採用の既存承認待ち。まだ加算しない |
| `complete` | 指定bundleが承認済みregistryに入り、active-productionとの整合も確認済み |
| `failed` | 通信の終端エラー・期限切れ・回答形式や本人性の検証失敗。自動再送しない |

既存のgenerate timerが両経路を同じgeneration lockで処理する。日次上限はUTCで合計3依頼。従来の非automaticモードでは同じバッチの合計3依頼を維持する。新しい日を理由に回答待ち・失敗済みのIDを再POSTしない。POST前にIDと送信時刻をfsync・原子的保存し、GET通信の失敗は同じIDで再確認する。外部送信許可を取り消すと以後の送受信は停止するが、既に送信済みの内容を撤回する機能ではない。

自動受付した投稿の通知には、保存済みの依頼状態を反映する。外部送信が無効なら「依頼待ち・未送信」であり、「Luna回答待ち」とは表示しない。同じ状態版での通知は再起動後も重複させず、既存の送信前永続化・応答不明時の返信照合を再利用する。明示コマンドは非公開の状態照会で追跡する。

### 独立検証と既存の採用手順への接続

Lunaの候補はmethod/evidence/code/conditions/uncertaintyを持つJSONで最大3件。codeは既存のAST拒否検査後、ネットワークなし・非root・読み取り専用・資源制限付きDockerだけで実行する。ホストへimport/execしない。未知のコードが動いたことや日本語を返したことだけでは採用しない。

独立根拠は、root所有のevidenceファイルで操作者が確認する。`schema:1`、`request_id`、`reply_sha256`、`candidate_index`、`source`、`selector`、`cases`、`public_synthetic_approved` を固定する。sourceは公開仕様・確認済み元文との対応・独立エンコーダーのいずれかと具体的reference、`operator_confirmed:true` が必要。Luna自身の主張や往復変換を独立根拠にはしない。共有した符号列とは重ならない検証例を3〜64件用意し、異なる正解本文を最低2種類、不正入力の拒否例を最低1件含める。

検証は `estimation.py --state <state> verify <依頼ID> --evidence <root所有JSON> --image <固定image>` で行う。確認は証拠の正しさについての操作者の責任を含む。テストに通っただけで方式の全入力について数学的な正しさを証明するものではない。

公開可能な合成依頼なら、全例一致後に既存の `proposals/<family>` と `jobs/<family>.json` へ接続する。最大3候補の原回答・選択indexを保存し、選んだcodeの抽出であることを明記した通常コードブロックも保存する。これにより既存CI/CD readerも独立検証を行える。**未知推定の候補は既存automaticレシピの自動公開対象にしない**。既存の手動公開差分承認、GitHub CI・受取側検証、本番採用DM承認が必要。

実投稿由来の回答は、独立検証に通っても公開bundleへコピーしない。`public_synthetic_reproduction_required` として保留し、別途、公開可能な合成入力だけで方法を再現・検証したproposalを用意する。`link-public` はfamily/selector・contractのハッシュ・独立goldの一致をDockerで再確認して既存採用手順へ接続する。実投稿や私的な対応表を公開する許可を推定依頼の送信許可から推測しない。

既存の審査JSONには新しいフィールドを追加しない。推定状態のキャッシュは `adaptive/estimation-status` に別保存し、本文版・epochと照合する。キャッシュだけの保存に失敗しても、永続化済み通知の依頼IDからGETで状態を復旧できる。旧版はこのサブディレクトリを無視して既存台帳を読める。配備時はBotとruntimeを同じ版で切り替え、台帳・累計を過去のバックアップで巻き戻さない。

### 再現検証

`python3 -m unittest discover -s scripts -p 'test_*.py'` と `go test -race ./...` はfakeを使い、実メッセージをDiscord/Lunaへ送らない。`scripts/evaluate-estimation.py --helper <同版のGo helper> --output <JSON>` は104件で受付と既定の送信抑止を評価する。これはLunaや感情判定モデルの推定精度を測るものではない。

`scripts/check-estimation-docker.py --work <新しい空ディレクトリ>` は、Lunaをfakeに固定し、固定ARM64イメージの実Dockerで6ケースを確認する。実投稿は使わない。通常日本語・無関係文字列・今回の4件は識別子を合成値にした例で検証し、実投稿由来の追加外部送信は別途、許可チャンネルと対象の選択文字列を具体的に提示して承認を受ける。
