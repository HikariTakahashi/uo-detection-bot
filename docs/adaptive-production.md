# Pi上の未知変換審査と本番カウント

Macは開発・初回配置にだけ使う。稼働中はPiのGo BotがDiscordとカウントを管理し、loopbackの復元サービス、既存Laya、systemd timerが処理を進める。

## 状態と返信

`adaptive.json` の `enabled: true` で有効。未設定なら既存処理を維持する。対象チャンネル・対象語・Bot/Webhook/DM除外は既存検知設定を継承する。完全一致・既存の連続語は従来処理、それ以外は永続審査キューが排他的に担当する。

未知変換は元投稿に1件だけ返信し、加算しない。審査記録には投稿/チャンネル/サーバー/投稿者ID、本文、編集時刻、版ハッシュ、最新の返信ID・過去の返信ID一覧、復元機能の版と状態を保存する。原文は外部生成サービスに送信しない。審査用ディレクトリは0700、記録は0600。待機上限1000件。上限では受付失敗をログに記録し加算しない。

新しい承認済み復元リリースまたは判定方針の版を検知すると待機投稿を再取得して判定する。現在はすべての保留投稿を候補に再確認するため、無関係な復元器追加でも再確認される場合がある。復元の適用はselectorで限定する。対応しない投稿は加算せず次版を待つ。既知復元器が拒否した入力でも、新しい独立検証契約で候補を特定できる場合は準備を更新する。ERROR/TIMEOUTの生成依頼を自動再送することはない。

返信文面は次のとおり。

```
冷笑の疑いがあるメッセージを検知しました！
<@{userId}>さんのメッセージは現在審査中です！
```

```
**再判定完了**
冷笑を検知しました！
<@{userId}>さんの{回数}回目の冷笑です！
```

```
**再判定完了**
冷笑ではありませんでした。
```

```
**審査継続**
判定が保留されました！
<@845282954636951583>、なんとかしろ！
```

再判定の結果（加算あり・対象外・保留）は、元投稿への新しい返信として各判定につき1件送る。最初の審査中の返信と過去の結果は編集せず残す。同じ本文版・同じ復元機能版の再試行では追加送信しない。保留は次のリリースで再判定したときに新しい結果を返信する。既存の完了済み審査は移行だけでは再送しない。メンション許可は指定ユーザーだけ。返信送信前にsendingを永続保存する。送信の応答が失われた場合、Bot自身の元投稿への返信のうち、前回の返信より新しく今回の文面と一致するものを履歴から照合し、別のPOSTを自動発行しない。履歴で照合できない場合は `review reply delivery unresolved` として運用者の確認を待つ。この場合まで「必ず自動で1返信」を保証する設計ではない。手動削除されたBot返信も再作成しない。

新形式の審査記録には `notice_version` と `reply_history` を保存する。旧版からの移行では未完了の返信編集だけを新規返信へ切り替える。旧バイナリは追加フィールドを読めないため、移行後のロールバックにはこの形式を扱える修正版を使い、審査台帳やカウントを過去のバックアップで上書きしない。

冷笑ワード件数を累計へ反映する。投稿全体に1つのラベルを付けて全語を加算せず、対象語のある文を判定する。どの文か不確かな場合は投稿を保留する。1投稿に複数語がある場合は複数回になる。通知の `{回数}` は加算確定時点の累計。

`counts.json` はreview_receiptsを含むversion 2に移行する。累計と投稿ごとの加算結果は同じファイルへ原子的に保存する。結果の返信送信を再試行しても再加算しない。審査ファイル更新直前のクラッシュでも、receiptから確定済みの累計を復元する。編集された投稿は最新版を取得し、以前の審査による寄与だけを取り下げて判定し直す。削除された未完了審査は取り消し、保存している審査中・結果のBot返信も削除する。完了済みの履歴を削除しても確定カウントを遡って取り消す運用ではない。

## Piの各サービス

- `discord-bot.service`: Gateway、審査台帳、返信、カウント。既存Bot資格情報を保持。
- 既存user unit `laya-shadow.service`: `/adaptive/detect` と `/adaptive/judge` を追加。固定済みのオフラインモデルを使用。
- `laya-decoder.service`: 127.0.0.1:8767。生成コードはネットワークなし・読み取り専用・非rootのDockerのみで実行。Python runner内部にもメモリ/CPU上限を設定し、Piのmemory cgroup無効時を補完。
- `laya-decoder-update.timer`: 2分ごとに `/etc/laya-decoder/approved-release.json` の固定commit/indexを確認。検証成功後だけsnapshotへのsymlinkを原子的に切り替える。
- `laya-decoder-generate.timer`: 1分ごとに承認済み合成テンプレートの依頼を進める。従来モードは1状態ディレクトリにつき新規依頼3件まで、自動モードはUTC日ごとに3件まで。POST直前にIDを保存し、応答不明時は同一IDのGETだけ。ERROR/TIMEOUTは自動再送しない。

デコーダーのtrusted controllerはdockerグループを使用するため、そのcontrollerとインストール済みソースはroot所有にする。生成コードにDocker socketや資格情報をマウントしない。Botのユーザーはdockerグループに加えない。

## 合成例・生成・公開・本番採用

未知検知後、Piはroot所有の `/etc/laya-decoder/automatic.json` で許可された公開仕様から、共有用サンプル3件と独立した正常・不正入力の検証契約を自動生成する。実投稿本文・ID・その可逆符号列はLunaへ送らない。生成器に渡す仕様と合成例、非共有の検証例は、Lunaの回答より前に固定する。生成コード自身から正解を作らない。

自動許可はroot方針のレシピ一覧に限定する。`x9:` はUTF-8各バイトを `(73*b+41)%256` に置換して大文字hexにする公開仕様。接頭辞なしの16進入力は通常hexとこの逆変換の競合候補として扱い、可読な復元結果が一意の場合だけ進める。これは「仕様も鍵も未知の方式を新たに解読した成功」ではない。方式が特定できないselectorは `needs_format_spec`、競合が残る場合は保留を維持する。

1. 外層・内層を問わず候補方式を最大8段探索し、未導入の復元器を形式ごとに準備する。`x9:` は専用prefix selectorを登録する。明示的なprefix復元器は広いshape復元器より優先する。
2. `laya-decoder-generate.timer` が合成準備、Luna依頼、本人性確認、隔離Dockerでの独立検証を進める。自動モードはUTC日ごとに新規3件まで。上限に達した未送信依頼は翌日へ持ち越す。送信前にIDを保存し、応答不明後はGETのみ。失敗/期限切れ/検証不一致は勝手に再送しない。
3. 公開可能な仕様・合成例だけをLunaへ送る。正解付き検証例は送らない。候補が全検証を通るまで本番は変更しない。
4. 自動公開方針を別途明示承認して `publish_validated=true` にした場合、`laya-decoder-publication.timer` が専用repoの更新案を作り、独立検証を再実行し、index・当該contract・bundleの最大5ファイルだけをCommit/Pushする。Pi専用トークンに対象repoのContents read/write、Actions readが必要。自動公開を許可していない場合は従来の具体的Commit承認で止まる。
5. 公開前にbase・title・全差分ハッシュを永続化。Commit後/Push応答不明でも同一Commitを再利用し、force pushはしない。差分ドリフト・遠隔競合は停止して既存結果を保持する。未決の本番採用DMがある間は次候補で置き換えない。
6. CI/Release成功と受取側の検証後、指定ユーザーへ本番採用DMを1件送る。DMで承認されてからPiが反映し、既存の待機投稿を最新版で再判定する。対象外・保留は非加算、確定分は台帳で二重加算を防ぐ。

`automatic` 導入モードは、具体的にレビューした自動公開範囲への承認後のみ実行する。BotやMacの資格情報は転用しない。従来のroot所有手動テンプレートは引き続き使用でき、その提案は自動公開の対象外。

## 導入

管理者がレビュー済み `scripts/install-adaptive.sh` をPiで実行する。

1. `prepare`: docker.io/gh/git、専用ユーザー、固定ARM64イメージを準備。本番Botを変更しない。
2. `credentials`: Pi専用GitHub tokenとLuna keyを非表示入力でroot専用ファイルへ保存。systemd LoadCredentialで各サービスに渡す。
3. CIの `decoder-production.tar.gz` と `ADAPTIVE-SHA256SUMS` を固定commitから取得し検証・展開。
4. `install`: runtime/service配置、Layaアダプターのバックアップ・更新、既存11復元器の固定Release再検証。本番カウントはまだ有効化しない。
5. 合成データで復元・再判定・health・権限・復旧を確認。
6. `enable`: 既存累計をバックアップし、新Botとadaptive設定を有効化する。既存チャンネル設定・Botトークンは書き換えない。

初期復元器の固定Releaseは `38a4bbc7bc6686b71745912aee845e8e89fa2520`。復元器11件は評価済みの成果物を明示的な本番承認記録とともに利用する。評価用manifestのscopeを書き換えたり、既存Releaseを上書きしたりしない。

`enable` は更新タイマーを一時停止する。新コードのGitHub main/Releaseと導入済みcommitが一致し、起動とhealthを確認してからBot更新timerを再開する。旧版への自動更新でv2状態を読めなくなることを避ける。

停止は `disable`。adaptiveの新規受付・加算を止め、累計とreceiptを維持する。停止後も動かす旧来の検知ルートとの重複を避けるため、既存レビューreceiptを持つ投稿は従来ルートから加算しない。旧バイナリへ戻すときはv2互換性を確認し、バックアップを現在の累計にそのまま上書きしない。

## Discord DMでの本番採用承認

`install-adaptive.sh approvals` で有効化する。既存の本番版と累計を引き継ぎ、従来の固定版更新timerを停止して `laya-decoder-approval.timer` に切り替える。Botの新しいバイナリと配布ソースを先に配置する必要がある。GitHub資格情報には専用評価リポジトリの Contents read に加えて **Actions read** が必要。

Piの `publication-pushed.json` に記録されたCommit/indexだけを候補にする。専用評価workflowの最新push実行が成功し、Releaseのハッシュ・全復元器の独立検証が通った後、ユーザー `845282954636951583` のDMに「本番採用を許可／却下」のボタンを1件送る。実投稿本文は送らない。合成準備・限定したGitHub自動公開への事前承認を代替しない。自動方針の範囲外は個別承認が必要。

回答期限は依頼作成から7日。催促は送らない。本人・DMチャンネル・Bot返信ID・依頼のハッシュを一致確認する。承認は候補Commit/indexと依頼時の本番版に固定され、候補や本番版の変更、期限切れ、却下では使えない。回答を永続化後、PiはCIと配布物を再検証し、同じ配備ロックの中で基準版の一致を確認して切り替える。成功後は既存の保留再判定を使う。DMは同じメッセージを編集し、反映完了・失敗・却下・失効を表示する。

現在版が承認済みの対象と一致し、記録が反映中なら、切り替え直後のクラッシュとして完了記録を復旧する。旧初期承認ファイルは定期処理で再適用しない。取得などの一時失敗は同じ承認だけで再試行し、検証不一致では旧版を保持して停止する。

承認連携は `/var/lib/laya-approvals` 配下だけを専用グループで共有する。requests/resultsはlaya-decoderのみ書き込み、decisionsはdiscord-botのみ書き込む。BotのDM送信記録は `/var/lib/discord-bot/release-approvals` に0700/0600で保存する。BotにsudoやDocker権限を追加しない。

DM拒否時はblocked記録を保持し、公開チャンネルへ転送しない。POST応答不明はBot自身のDM履歴を照合し、見つからなければ再POSTせず運用者確認を待つ。手動で消されたDMも自動再作成しない。却下・失効済みの同じ候補は再通知しない。再依頼が必要な場合は、通常のapprovalサービスと同じユーザー・資格情報・環境で `approval.py` に `--retry-request <終了済み依頼ID>` を指定する。再検証後に新しい依頼ID・期限で作成する。

Piで確認した配備条件として、3つのdecoderサービスのTMPDIRは書き込み可能な専用StateDirectoryを使う。runtime制御プロセスの仮想アドレス上限はDocker CLIが起動できる2GiB、生成コード内部のアドレス上限は128MiBを維持する。Lunaリレーへの通信はアプリ名のUser-Agent `uo-decoder-pi/1.0` を明示する。

## 接頭辞なし・多重変換の候補準備

`automatic` の許可範囲は x9、接頭辞なし16進候補群（通常のUTF-8とx9逆変換）、Base64、Base32、percent、Unicode escape。形式の見た目だけで鍵や本文を決めず、ローカルの厳密な逆変換・UTF検証と独立した前向きエンコーダーを根拠に候補を絞る。16進候補が複数の異なる可読本文を返す場合は保留し、対象ワードに近い候補を優先しない。通常の16進復元器を承認済みでも、新しい競合候補契約の承認を代用できない。

候補推定は最大8段。実投稿や中間の復元本文はPi外へ送らず、発見記録には形式・候補方式・深さだけ保存する。候補による復元は合成データ準備のためだけに使い、本番の判定・加算には使わない。実行されるのはLunaが生成し、固定した独立契約、GitHub CI、Piの受取側検証、本番採用DM承認を通った復元器のみ。途中の未対応形式も準備し、複数の復元器が必要なら各リリースの承認後に次の候補を公開する。1日3依頼、各公開は復元器・契約・indexの最大5ファイル、force push禁止を維持する。

本番稼働中はPiで完結する。仕様自体が未知で独立した正解を作れない形式、候補競合、探索上限、生成失敗は自動採用しない。この変更で任意の暗号方式・未知鍵を復元できるようになるわけではない。
